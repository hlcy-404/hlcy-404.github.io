# 本地写作使用指南

适用范围：Windows 本机运行的写作组件。1.2 起按用户更新的决定，源码、测试、依赖锁文件与启动器可随博客仓库分发。公开源码不会启动服务，也不会授予访客编辑权限；草稿、备份、会话和运行时均不上传。

本地写作界面用于新建文章、填写信息、编辑正文、插入图片、保存草稿、查看博客真实主题，以及确认后发布到 GitHub。正式文章仍是 Markdown 文件，没有新增数据库。

## 打开和关闭

1. 双击项目根目录 `studio.cmd`，浏览器会打开 <http://127.0.0.1:4010/>。
2. 写文章和保存不依赖 Docker。需要真实预览或发布前检查时，先启动 Docker Desktop。
3. 结束使用时双击 `stop-studio.cmd`。关闭浏览器后本地服务继续跟踪部署；关闭服务会暂停查询，下次启动恢复。若仍在本地构建或上传，会提示先等待完成。

首次启动会从 Node.js 官网下载固定版本 24.22.1 并核对 SHA-256，在项目 `.local/runtime/` 解压；随后按 `tools/studio/package-lock.json` 安装本地依赖。不会修改全局 Node/Ruby，也没有开机启动或自动推送。依赖已准备好后，写作界面可离线启动。

编辑端口为 `127.0.0.1:4010`，真实预览为 `127.0.0.1:4011`，两者只允许本机访问；常规 `preview.cmd` 仍使用 4000 端口。

## 写一篇文章

- 点击“新建文章”，选择空白、研究记录、工程实践、阅读笔记或随笔模板。
- 填写标题、英文短名称、摘要、北京时间、分类和标签。分类/标签用中英文逗号分隔。英文短名称使用小写字母、数字和短横线，例如 `agent-reading-notes`。
- 在正文工具栏插入标题、粗体、列表、引用、链接、代码块和公式。正文使用 Markdown，可直接粘贴已有内容。
- 图片可以通过“插入图片”、拖入或粘贴加入。支持 PNG、JPEG、GIF、WebP，单张不超过 10 MB；保留原图，自动生成稳定文件名。
- 输入后自动保存，也可点击“保存”。离开前确认页面显示“已保存到本机”。同一草稿在多个窗口编辑时，旧版本保存会被拒绝，避免静默覆盖。
- “导出文章”下载包含 Markdown、文章信息、引用的本地图片与附件的 ZIP；“导入文章”支持新 ZIP 和已有 v1 JSON。旧自动恢复副本位于 `.local/studio/backups/`，新版历史位于 `.local/studio/history/`，均不上传。恢复会创建新版本，原内容继续保留。

## 完整备份与恢复

1. 先保存各窗口输入，打开右上角“备份与空间”，点击“生成备份”。生成时核对已保存文件，不包含仍在浏览器中的未保存输入。
2. ZIP 包含当前网站源文件、工具源码与锁文件、草稿与配图、版本历史、旧恢复副本及发布记录。每个文件有 SHA-256 清单；Git 历史/凭据、运行时、安装依赖和可重建预览不在包内。
3. 点击“下载”，另存到其他设备或磁盘。只在同一台电脑生成副本不能防止整机或硬盘损坏；界面不会声称已完成离机备份。
4. 恢复时选择完整 ZIP，先查看草稿数量、版本、文件数和恢复位置，再点击“确认恢复独立副本”。副本位于 `.local/studio/restores/<编号>/project/`；原项目、文章和草稿保持不变。
5. 停止当前编辑服务，在恢复目录内运行 `studio.cmd`。首次启动需联网准备固定版本 Node.js 和依赖；真实预览仍需 Docker Desktop。恢复副本可以编辑、查看历史、重新预览和导出文章。
6. 恢复副本不连接 Git、不自动运行包内代码、不继续旧发布确认。核对后可导出单篇文章包，导入正式项目发布。旧任务在 `restored-records/` 中保留。

新 ZIP 上限为压缩前/后各 256 MiB，单文件 64 MiB，最多 12000 个文件；超限明确停止。原图片上传仍限 10 MiB，旧 JSON 导入仍限 64 MiB。文件损坏、缺失、重复路径或链接目录会拒绝恢复。完整包包含工具代码，应仅使用自己生成或可信来源的备份。

## 完整文章包

- 包内 `article.md` 可直接阅读，`assets/` 保留引用资源；`draft.json` 供工具导入，`manifest.json` 包含完整性校验及外链清单。不要手工修改包后仍将其当作原始校验备份。
- 覆盖 Markdown 图片/附件/引用式链接、HTML 的 `src`、`href`、`poster`、`srcset`，以及文章信息中的封面和明确资源路径。支持静态 `relative_url` / `absolute_url` 写法。代码示例保持原文。
- 包内地址改为相对路径；导入时重新生成草稿编号和本地资源地址，不覆盖已有文章。合法自定义字段保留，固定 permalink 与发布关联清除。
- 外部资源不会自动下载；原站点页面导航和外链列在清单中，仍依赖原网站。缺失的本地文件会阻止导出。动态 Liquid、内嵌页面/脚本、样式资源等不作完整性承诺，发现时提示改成明确的静态资源。

## 存储占用与清理

“备份与空间”按草稿与配图、历史、预览、备份及恢复副本统计 `.local/studio/`，并显示所在磁盘余量。浏览器暂存、Node 运行时和 Docker 卷不计入此处的写作数据占用。

375px 窄窗口下，标题和关闭按钮保持可见，列表与摘要跟随一个内容区域滚动。可以用 Tab / Enter 选择备份，核对摘要生成后会自动显示；Escape 关闭后返回入口。选择新文件会使旧恢复确认失效，校验失败时不会继续使用上一份摘要。

旧预览可勾选后“清理所选”，再次确认才删除。每篇文章最近一次成功预览、正在运行的任务以及标记“保留”的预览均受保护；确认期间状态或文件改变会要求重新核对。清理后旧链接明确显示文件不可用，不跳到其他预览。正文、配图、版本历史、备份包和恢复副本不在当前清理功能范围内。

点击仓库文章会创建本地修订副本，不立即修改 `_posts/`。已有文章的短名称固定，改标题不会更改公开网址；原 YAML 信息区中不在表单内的字段会保留。

## 版本恢复、浏览器暂存与冲突

- 点击“版本历史”，选择版本后查看红绿差异和完整原文，最后点击“确认恢复为新版本”。恢复保留现有文章地址、源文件关联和发布记录；缺失配图会阻止恢复。
- 自动保存之前，输入会在约 300 毫秒后暂存于当前浏览器。只有实际写入成功才显示暂存状态。服务断开后重开页面，点击顶部“查看暂存”核对并恢复；待上传图片也会保留，恢复后点击“重试插入”或“取消插入”。浏览器存储可被清除，不能替代项目文件备份。
- 多窗口冲突会暂停自动保存。系统基于共同原稿生成建议，选择冲突段落或手动编辑后确认。期间出现新修改会再次核对，保留已整理的结果；没有可靠原稿时改为手动比较。点击“稍后处理”会暂存整理结果，稍后从“处理冲突”继续核对。
- “导入备份”接受 v1 JSON（不超过 64 MiB，单图不超过 10 MiB），校验后创建独立草稿并重写随包图片路径，不覆盖原稿。已发布地址关联被移除；重复短名称需修改。图片未随包携带而存在于当前项目时会明确提示，缺失则导入失败。失败不会出现半成品草稿。
- 浏览器存储不可用时会持续提示，并提供导出/复制当前正文。正式保存、恢复和导入都只写入本机；没有自动上传或自动清理。

## 预览

“快速排版预览”适合检查普通 Markdown 结构。公式、Mermaid、Liquid 和主题特有组件，请点击“真实主题预览”检查。

真实预览把当前网站源文件与所选草稿复制到 `.local/studio/builds/<操作编号>/source/`，使用本项目 Docker 和 Chirpy 7.1.1 构建，执行 HTML-Proofer；构建成功后点击“打开预览”，可切换桌面/手机宽度，也可在新窗口打开。地址为 `http://127.0.0.1:4011/previews/<构建编号>/…`，页面、图片和样式固定属于这次构建；工具栏显示预览/当前版本、构建时间，以及内容或网站源文件是否发生变化。其他草稿不会进入这次构建，正式 `_posts/` 与常规 `_site/` 不被改写。

预览关闭 PWA，避免把草稿留在浏览器离线缓存中。主题公式等外部脚本仍可能需要联网。构建记录保存在本机，包含主题原有的 Sass 弃用提示；它们不代表构建失败。

旧版预览记录没有固定快照元数据时需要重新生成，原构建文件不删除。仅支持仍保存在本机的预览地址；文件缺失会提示，不会显示其他构建。

## 发布与跟踪

1. 保存后点击“检查并发布”。按钮首先检查仓库状态并构建文章，不会立即上传。
2. 检查通过后，阅读文章/配图清单以及“原内容—本次内容”，再点击“确认发布到 GitHub”。
3. 工具只提交本次核对的文章和所引用的新配图，正常推送到 `origin/main`。原先的全项目 `sync.cmd` 保留不变。
4. 本地服务按本次提交编号跟踪 Pages 工作流，关闭编辑页后继续查询。重开后在顶栏“发布记录”查看卡片；每条记录含文章标题、提交、阶段和检查时间。默认约每 90 秒探测，页面仅读取本机状态。
5. “上传失败”提供“重试上传”，仍使用原提交；“构建失败”“部署失败”提供构建详情和“重新检查”。后者只重新读取状态，不会重跑 Actions。解决原因并在 GitHub 重跑后，可重新检查最新运行尝试。
6. “上线成功”要求工作流成功、公开文章的 studio-revision 与本次版本完全一致、随篇资源哈希匹配；仅 HTTP 200 或工作流结束不能替代上线确认。等待任务或公开版本超过 30 分钟仍未通过时停止自动等待并提示重新核对。
7. 网络故障、接口限流保留最近已知阶段，逐步延后查询并遵守 GitHub 的重试时间。停止服务时记录保留，下次启动恢复；电脑关闭或服务停止期间不查询，也不安装开机常驻任务。恢复出来的独立工作副本不接续旧发布。
8. 上传完成后若本机发布记录更新失败，会单独显示本机记录问题，不标成上传失败。检查日志、失败详情、文件清单及正文差异可按需展开。

**使用发布按钮之前，需要先处理未同步的项目开发改动。** 1.2 源码及此前站点改动已同步；后续仍要求分支为 main、目标仓库正确、工作区干净，并与远端一致。若存在未提交的界面改动、已有暂存文件、未推送提交或远端新版本，会显示具体原因并暂停，保留草稿和所有修改。这不是草稿保存失败。先审阅修改清单，再使用既有 `sync.cmd` 处理整个项目的改动，最后回来发布文章。

首版没有定时发布。未来时间会被提示修改为当前/过去日期，或继续保存为草稿。GitHub 已部署不等于旧浏览器缓存自动刷新，遇到“发现新版本的内容”时点击“更新”。

## 复用组件与维护

| 组件 | 用途 | 固定版本 |
| --- | --- | --- |
| EasyMDE | Markdown 编辑、工具栏、CodeMirror 输入 | 2.21.0 |
| DOMPurify | 快速预览的 HTML 清理 | 3.4.17 |
| node-diff3 | 差异比较和三方合并建议 | 3.2.1 |
| fflate | ZIP 打包与有界解压 | 0.8.3 |
| marked | 服务端文章资源识别 | 18.1.2 |
| yaml | 读取和更新文章信息区，保留未知字段 | 2.9.1 |
| Node.js | 本地文件与发布服务 | 24.22.1 |
| Jekyll / Chirpy / Docker | 博客真实主题构建与检查 | 沿用项目既有依赖，Chirpy 7.1.1 |
| Git / Credential Manager / GitHub Actions | 认证、上传及 Pages 部署 | 沿用现有本机和仓库配置 |

编辑器脚本和样式均从本地依赖读取，没有通过 CDN 引入编辑器。前端不接收或保存 GitHub 密钥；推送使用本机现有凭据。GitHub 登录过期时需要先通过原有 Git 认证流程恢复。

第三方许可和来源见 `tools/studio/THIRD-PARTY.md`。Front Matter CMS 与 Decap CMS 是可替代的完整内容管理工具，本次没有额外安装它们。

## 本地回归

```powershell
# 不向 GitHub 推送：在 .local/studio-tests 内创建临时仓库和本地 bare 远端
.\.local\runtime\node-v24.22.1-win-x64\node.exe --test tools/studio/test/*.test.mjs

# 常规生产站点构建检查，测试草稿不会进入正式输出
docker compose run --rm blog bash -lc 'bash tools/test.sh'
```

发布逻辑的自动回归使用本地测试远端；部署成功、失败、旧页面等状态使用受控响应验证。正式 GitHub 发布仍需要用户确认后，以该次真实提交和线上页面验收为准，不能用这些本地测试替代。
