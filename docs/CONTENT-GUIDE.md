# 内容与创作流程

## 发布一篇文章

1. 在 `_posts/` 创建 `YYYY-MM-DD-english-slug.md`，先从 `docs/templates/POST.md` 复制。
2. 填写标题、日期、摘要、分类、标签。摘要建议 60–120 个中文字符，明确问题、做法与读者收获。
3. 图片放 `assets/img/<slug>/`，文件名可读；添加替代文字和来源说明。
4. 双击 `preview.cmd`，检查首页列表、文章正文、代码、公式、图片、手机阅读。
5. 构建与检查通过后，用户明确决定发布再运行 `sync.cmd`。

未来日期文章默认不会出现在生产站点。草稿存 `_drafts/`，或设 `published: false`；公开仓库本身不适合存私密草稿。`hidden: true` 仅隐藏首页条目，不能保护内容。

## 建议内容组织

分类优先按内容目的：研究记录、工程实践、阅读笔记、随笔。标签描述具体技术，如 Agent、评测、部署。先保持少量分类，避免每篇文章建立一个新类别。项目数量足够后，再单独设计项目集合。

研究记录推荐顺序：问题 → 背景/已有方法 → 方法与假设 → 证据/实验 → 结果 → 局限与下一步。给出来源日期，不把推断写成事实。

工程记录推荐顺序：需求 → 环境/版本 → 方案取舍 → 实现 → 验证 → 复现步骤 → 已知限制。性能结论给出硬件、输入规模、基线与测量口径；失败实验也可以成为有用内容。

## 现有能力的使用

- `pin: true`：在首页优先显示适合作为入口的文章。
- `math: true`：按需启用主题公式功能，具体浏览器加载需验收。
- `mermaid: true`：按需启用主题图示功能；含外部资源，发布前检查。
- `toc: true`：长文目录。标题层级从二级开始，避免一个页面多个主标题。
- `description`：供首页摘要与搜索使用；不要直接填正文开头的无信息引言。
- `last_modified_at`：需要人工注明更新时使用，避免把普通格式调整写成重大内容更新。

## 发布前内容检查

确保所有履历与成果有依据；实验值可追溯；引用可访问；代码不含密钥/内部地址；照片与截图可公开；标题/摘要准确；正文中的链接与附件有效。涉及他人数据时只使用有权公开的内容。

## 维护友链

在 `_data/friends.yml` 中维护姓名、英文显示名、字母标识、关系、简短介绍、可选 Markdown 长简介、研究方向、个人主页和可选合作文章。经用户提供的照片放在 `assets/img/friends/`，填写路径及原始宽高；不提供照片时显示字母标识。只加入用户确认的人物，公开资料以本人主页为准，不推测 GitHub 账号，不从其他人的友链页批量复制人物或联系方式。页面由 `_tabs/friends.html` 渲染，地址 `/friends/`；更新后检查外链、375px 布局与夜间模式。

`homepage_label` 可区分“访问个人主页”和“查看原友链介绍”等链接用途。引用第三方人物介绍时，不把未注明年份的分区或影响因子写成当前指标。
