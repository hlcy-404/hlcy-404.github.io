# 本地文章编辑与 GitHub 发布方案

日期：2026-10-26。状态：首版已按此方案在本地实现。具体入口、已实现范围与使用限制以 [本地写作使用指南](LOCAL-STUDIO.md) 为准；下文保留方案选择和设计依据，后续扩展不等同于已实现功能。

建议在当前项目内增加一个仅在本机运行的写作界面。通过表单填写文章信息、编辑正文和插入图片，使用现有 Jekyll 主题预览，核对后点击发布，由本地服务提交到 GitHub，随后跟踪 Pages 部署。保留现有 Markdown 内容、文章地址和主题，避免迁移博客。

## 现状与需要补齐的能力

当前项目已有 `_posts/`、文章模板、Docker 预览、Git Credential Manager、同步脚本及 Pages 工作流；缺少新建文章表单、图片管理、草稿状态和发布进度界面。

`tools/Sync-Blog.ps1` 当前会提交全部改动，并在推送后结束。因此不能把它直接接到“发布当前文章”按钮：需要增加明确的文件范围、发布前构建、失败恢复及部署状态追踪。原 `sync.cmd` 继续用于人工同步整个项目。

GitHub Pages 是静态网站托管服务；编辑界面可以运行在本地，但保存文件、调用 Git 和管理发布需要本机服务承担。公开站点继续只展示阅读页面。[GitHub Pages 官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

## 方案比较

| 方案 | 优点 | 成本与限制 | 适用情况 |
| --- | --- | --- | --- |
| 本地浏览器写作界面 | 中文操作可按需求设计；新建、插图、预览与发布在同一界面完成；可复用现有博客 | 需要开发和维护一个小型本地服务及发布流程 | 希望日常写作脱离代码编辑器，推荐 |
| VS Code 加 Front Matter CMS | 已有元数据表单、Jekyll 草稿支持、模板和站点预览，起步成本低 | 日常操作仍在 VS Code；本项目的精确发布范围和 Pages 状态需要单独接入 | 接受编辑器工作流，希望尽快开始写作 |
| Decap CMS 加 GitHub 后端 | 可在浏览器管理内容，适合跨设备或多人协作 | 需要配置 GitHub 认证服务或托管认证；本地修改与远端编辑还需处理同步 | 将来确实需要手机、异地设备或多人编辑时 |

Front Matter 官方文档列出了文章字段及 Jekyll `_drafts`、`_posts` 支持，并提供连接本地站点的预览配置；这些是产品能力，不代表已在本仓库验证。[字段说明](https://frontmatter.codes/docs/content-creation/fields/) · [站点预览](https://frontmatter.codes/docs/site-preview/)

Decap 的 GitHub 后端需要仓库推送权限和认证配置，官方给出了认证服务及托管认证选项。对当前单人本地写作，额外维护成本较高。[GitHub 后端说明](https://decapcms.org/docs/github-backend/)

## 推荐的日常流程

1. 双击项目根目录的 `studio.cmd`，打开本地写作页面；启动器准备运行时，页面提示 Git 和 Docker 是否就绪。
2. 点击“新建文章”，选择空白、研究记录、工程实践、阅读笔记或随笔模板。模板只提供结构，不虚构正文。
3. 填写标题、摘要、分类、标签和发布日期，编辑正文；粘贴或拖入图片，填写图片说明。
4. 自动保存到本机草稿，显示最近保存时间；支持手动保存和关闭后恢复。
5. 点击“预览”，用当前博客的真实主题查看文章，同时检查首页列表、图片、代码、公式与目录。
6. 点击“发布”，查看本次文章、配图和内容差异；确认后执行检查、提交、上传和部署跟踪。
7. 部署成功后显示公开文章链接；如果仍在构建、失败或无法读取状态，分别说明，不能提前显示“已上线”。

发布后的文章可以再次打开编辑。修改先保存为本地修订，点击“更新文章”后沿用相同流程与原网址。

## 首版界面与功能

| 区域 | 首版内容 |
| --- | --- |
| 文章列表 | 本地草稿、已发布、待更新；标题搜索、最近修改时间、新建按钮 |
| 文章信息 | 标题、英文短名称、摘要、日期与时区、分类、标签；置顶、目录、公式开关 |
| 正文编辑 | Markdown 编辑与即时预览；标题、粗体、列表、链接、图片、代码块、公式的工具栏；中文输入法正常 |
| 图片 | 拖入或粘贴、自动生成安全文件名、显示体积、添加替代文字；初版保留原图，压缩为后续可选操作 |
| 真实站点预览 | 复用 Jekyll + Chirpy；桌面和手机宽度切换；提示即时 Markdown 预览与正式主题可能有差异 |
| 发布面板 | 文件清单与差异、检查结果、上传状态、部署结果、公开链接、失败原因和可执行恢复步骤 |

先采用带工具栏的 Markdown 编辑器，可以稳定保留科研文章中的公式、代码和现有 Liquid 内容。完整 Word 式自由排版放在后续评估；导入现有文章时必须保留未识别的 front matter 字段，不能因编辑器不支持而删除。

## 工程结构建议

首版采用下列目录；实际操作说明见使用指南：

| 路径或组件 | 作用 |
| --- | --- |
| `studio.cmd` | 手动启动写作界面，不安装开机自启或文件自动上传 |
| `tools/studio/` | 本地页面、文件接口、校验和发布协调；固定依赖及锁文件 |
| `.local/studio/drafts/<id>/` | 草稿正文、图片与文章信息；利用已有忽略规则保持本地 |
| `.local/studio/backups/` | 草稿与文章修订的保存前恢复副本；未发布修订同样在 drafts 中维护 |
| `.local/studio/builds/` | 预览源副本及构建结果，避免与常规 `_site` 同时写入 |
| `.local/studio/jobs/` 与 `releases/` | 本次发布快照、进度、提交编号和文件恢复副本；不存凭据 |
| `_posts/YYYY-MM-DD-slug.md` | 点击发布后生成或更新的正式文章 |
| `assets/img/posts/<slug>/` | 本次发布文章引用的图片 |

建议使用项目专用 Node.js LTS 运行本地服务，复用宿主机 Git 和已有 Git Credential Manager；Jekyll/Ruby 继续运行于现有 Docker。实施时固定并验证运行时与依赖版本，运行时放项目本地目录，不修改全局 Node/Ruby，也不要求在网页填写 GitHub 令牌。编辑器服务无需数据库，Markdown 和图片仍是可迁移的内容来源。

服务只绑定 `127.0.0.1`；写入操作校验会话与来源，限定仓库内允许目录，使用参数列表调用 Git，避免将标题或正文拼进命令。预览与编辑器接口分离，文章内容不能执行编辑器的发布操作。开发工具和本地数据明确排除于 Jekyll 发布产物。

草稿在 `.local` 中不会同步 GitHub，因此应提供导出草稿包及本地恢复副本。`published: false` 和 `_drafts/` 只影响网站生成，不应作为公开仓库里私密草稿的保护手段。

## 发布按钮的具体行为

保存仅写本地文件。只有在发布面板确认文章及配图后才触发上传，发布过程中锁定该次快照并禁用重复点击。

1. 校验标题、唯一短名称、日期、YAML、图片路径和文件大小；生成预期公开地址。已发布文章固定短名称，改标题不自动改网址。
2. 检查分支、目标仓库、冲突和远端状态。首版若存在未处理的远端变更、已有未推送提交、已有暂存内容或本次范围外的未提交修改，则暂停发布并显示文件/原因，保留所有修改。这样可以先避免复杂 Git 合并与误发。
3. 在隔离目录构建准备发布的快照，检查文章页、首页入口、站内链接和资源；不读取其他本地草稿作为发布输入。
4. 构建通过且快照未变化，才将选中文章与配图写入正式目录并精确提交；不使用全仓库 `git add -A`。对既有文章先保存恢复副本。
5. 正常推送到 `origin/main`。远端在检查后发生变化时，推送失败并保留本地提交，不强推，也不自动抹掉用户内容。
6. 按本次提交编号匹配 Pages 工作流，显示“已上传，部署中”；等待同一提交的构建和部署完成，再核对公开文章内容与资源，处理既有 PWA 更新提示。
7. 推送网络失败时重试同一个提交；构建失败时返回编辑；部署失败时保留日志入口；状态查询超限或断网时显示“待确认”，不重复创建发布提交。

状态应区分：本地草稿 → 检查中 → 已提交 → 已上传 → 部署中 → 已上线。阶段失败保留已完成的状态，页面重开后可以根据本次提交编号继续查询。

未来日期不等于自动定时发布：当前工作流不会仅因时间到达而重建。首版提示改为立即发布或继续保存草稿，暂不承诺定时上线。

## 实施顺序与验收

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| 一 本地写作 | 启动入口、文章列表、表单、模板、正文、图片、自动保存和恢复 | 不使用 AI 也能独立完成文章；重启后内容不丢；草稿未进入 Git 和正式网站 |
| 二 真实预览 | 独立预览副本、主题渲染、桌面/手机检查、内容校验 | 中文、长标题、图片、代码、公式、目录正常；原有文章导入再保存无内容损失 |
| 三 发布闭环 | 明确文件范围、发布确认、构建、Git 推送、部署跟踪、公开链接 | 只发布当前文章和配图；分叉、鉴权失败、断网、重复点击、部署失败可恢复；公开站点显示本次内容 |

首版不加入 AI 自动写作、多人权限、评论后台、数据库、定时发布或自动清理图片。核心目标是让本人能稳定完成“写作—预览—发布”；后续再考虑 Word 导入、引用文献辅助、图片压缩、多设备草稿同步和 AI 可选润色。

## 结论

选择本地写作界面最符合“在本地项目填写内容并点击发布”的目标。先完成小而完整的单人写作与发布流程，继续沿用现有博客和 GitHub Pages；如果希望先用现成工具开始写作，Front Matter CMS 是成本较低的替代路径。
